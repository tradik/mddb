## Bulk Ingest Throughput

Indexing a document touches three full-text indexes, and each entry point used
to open its own BoltDB write transaction — so a batch paid three commits per
document. Batching a whole chunk into one transaction (GO-027) leaves the work
unchanged and removes the commits.

| | Before | After |
|---|---|---|
| 1000 documents, indexed | 4.20 s (**238 docs/s**) | 0.14 s (**6 996 docs/s**) |
| Allocated | 452 MB | 68 MB |

Measured with `go test -bench BenchmarkBulkIngest -benchmem -run '^$' .` in
`services/mddbd`. The same benchmark with `SkipFTS` reports ~57 000 docs/s,
which is the cost of the document writes alone — indexing was 99.5% of the
time before this change.

The batched index is byte-for-byte identical to the per-document one; a test
compares every FTS bucket entry between the two paths rather than checking
that search still returns something.

## Notes

- **tfidf**: Fastest for simple keyword matching. No length normalization.
- **bm25**: Slightly more compute than tfidf due to document length normalization. Best general-purpose algorithm.
- **bm25f**: Adds field-level weighting. Slower due to separate field index lookups.
- **pmisparse**: First search triggers lazy PMI matrix training (not included in benchmark). Subsequent searches include PMI expansion overhead.
- **fuzzy**: Adds Levenshtein distance computation. Expected ~2-3x slower than exact matching.
- All benchmarks run on a warm server with FTS indices already built during document insertion.

## Retrieval quality on the MDDB docs (v2.18.8)

The latency tables above say how fast each algorithm is. This section says how
often it finds the right page. The set is
[`tools/bench/evalsets/docs.json`](https://github.com/tradik/mddb/blob/main/tools/bench/evalsets/docs.json): 20
questions about MDDB, each with the documentation page that answers it, graded
0–3. The questions are phrased the way a user asks, not copied from headings.
The collection is the 60 pages of `docs/`, keyed by file name.

Measured 2026-10-29 on a default-configured server built from this release.
Embeddings came from `nomic-embed-text` through Ollama, autodetected.

```bash
mddb-cli eval docs --queries tools/bench/evalsets/docs.json \
  --config fts/bm25 --config fts/bm25f --config fts/tfidf --config fts/pmisparse \
  --config vector --config hybrid
```

| Configuration | recall@10 | nDCG@10 | MRR | p50 ms | p99 ms |
|---------------|-----------|---------|-----|--------|--------|
| fts/bm25 | 0.825 | 0.739 | 0.723 | 0.9 | 1.9 |
| fts/bm25f | 0.825 | 0.739 | 0.723 | 0.8 | 1.2 |
| fts/tfidf | 0.800 | 0.496 | 0.405 | 1.0 | 1.1 |
| fts/pmisparse | 0.800 | 0.574 | 0.535 | 0.9 | 33.6 |
| vector | 0.875 | 0.763 | 0.750 | 20.1 | 44.2 |
| hybrid (alpha 0.5) | 0.875 | 0.783 | 0.765 | 10.7 | 17.3 |

- **Hybrid ranks best.** It finds as many pages as vector search and puts the
  answer higher: its MRR is 0.765, against 0.723 for BM25.
- **TF-IDF finds the pages but ranks them badly.** Its recall is close to
  BM25, but its MRR is about half.
- **BM25F equals BM25 here.** These documents have no separate title field to
  weight.
- **Some questions share no words with their answer.** "import a million
  documents in the background" should find the bulk-import page. Keyword
  search misses it and vector search finds it. Those questions are where
  vector search earns its latency.
- **Two questions defeat every configuration.** These are "call my endpoint
  when a document changes" (automations) and "which documents are read most
  often" (temporal tracking). The pages never use the asker's words. That
  points at the pages, not at the search.
- **Returned tokens are large because every result is a whole page.** With
  `format: passages` an agent receives a fraction of that.

The same set runs in CI with keyword search only. The test is
`TestEval_DocsSetHoldsTheLine` in `services/mddbd/eval_docs_test.go`. It fails
when recall@10 drops under 0.7 or nDCG@10 under 0.65. The test server there
scores 0.750 and 0.683, because it does not use a default server's
configuration.

## BM25 parameters on the MDDB docs (v2.18.8)

Same corpus and the same 20 questions as above, keyword search only. Only
the BM25 parameters change. Measured 2026-10-29 with:

```bash
mddb-cli eval docs --queries tools/bench/evalsets/docs.json \
  --config fts/bm25 --config fts/bm25:k1=1.2:b=0.3 --config fts/bm25:k1=0.6:b=0.75 \
  --config fts/bm25:k1=2:b=0.75 --config fts/bm25:b=0
```

| k1 | b | recall@10 | nDCG@10 | MRR |
|----|---|-----------|---------|-----|
| 1.2 | 0.75 (default) | 0.825 | 0.739 | 0.723 |
| 1.2 | 0.3 | 0.825 | 0.685 | 0.660 |
| 0.6 | 0.75 | 0.825 | 0.676 | 0.644 |
| 2.0 | 0.75 | 0.825 | 0.749 | 0.731 |
| 1.2 | 0 | 0.800 | 0.523 | 0.438 |

- **Recall barely moves.** The parameters change the order, not what is found.
- **Length normalisation matters here.** These pages run from 39 to almost 20,000
  words, and with `b = 0` the long pages win on repetition alone.
- **The textbook advice points the wrong way.** It suggests a lower `b` for
  short questions, but here it made ranking worse. The one gain came from a
  higher `k1`, a small one.
- **Why the advisor works only from measurement.** It tries `b = 0.3`,
  `k1 = 0.6` and `k1 = 2` on a collection's own evaluation set. It
  recommends a variant only when that variant scores better. There are no
  thresholds on document length behind it.

## Finding code: grep and read vs MDDB passages (v2.18.8)

An agent asked to change something first has to find it. This compares the
two ways it can, on the MDDB repository itself. The comparison counts tokens
and tool calls. It does not measure answer quality.

The 15 tasks are in
[`tools/bench/evalsets/agent-tasks.json`](https://github.com/tradik/mddb/blob/main/tools/bench/evalsets/agent-tasks.json).
Each has a question, the term an agent would grep for first, and the file
that holds the code.

- **grep + read (best)** greps the tracked files, which is what ripgrep
  searches. Output is capped at 250 lines, as agent grep tools cap it. Then
  it reads only the answer file. This is a lower bound, because it assumes
  the agent picks the right file first.
- **grep + read (typical)** greps the same way, then reads the matching
  files with the most matches first until it reaches the answer.
- **mddb** makes one search that returns passages (`format: passages`,
  5 results). The answer counts as found when a passage comes from the
  answer file.

Measured 2026-10-29 on this release. The collection was made with
`mddb-cli autoindex .` from the repository root: 1491 files, 14.5 MB.
Embeddings came from `nomic-embed-text` through Ollama. Tokens are bytes
divided by 4.

```bash
cd tools/bench
go run ./agent -url http://localhost:11023 -collection mddb -root ../.. \
  -tasks evalsets/agent-tasks.json -search vector
```

| Route | Tokens, 15 tasks | Tool calls | Answer reached |
|---|---|---|---|
| grep + read (best) | 139,959 | 28 | 13/15 |
| grep + read (typical) | 2,769,973 | 133 | 13/15 |
| mddb vector, passages | 84,977 | 15 | 13/15 |
| mddb hybrid, passages | 41,666 | 15 | 10/15 |
| mddb fts, passages | 56,284 | 15 | 6/15 |

- **Vector passages match grep on answers found.** They use 0.6× the tokens
  of grep's best case and about 3% of its typical case. They take one call
  per task. Grep takes two in its best case and up to 33 in its typical
  case.
- **Grep's typical case is expensive because common terms match widely.**
  "revision" matches about 160 tracked files, so reading the most-matched
  files first takes 21 reads before the answer.
- **Full-text passages miss most of these questions.** The questions are
  phrased as a person asks them, and the code does not use the same words.
  One question starts with `--fail-below`, which the full-text parser reads
  as an exclusion, so it returns nothing.
- **Hybrid sits between the two here.** On this set it is pulled down by the
  full-text half. Run `mddb-cli eval` on your own questions before picking
  one, as shown in
  [Measuring Instead of Guessing](SEARCH.md#measuring-instead-of-guessing-v2188).
- **Two tasks defeat grep.** For "include paths" and "cross-collection text
  search", the first term an agent would try is not in the answer file.

The tool prints per-task rows as well, and `-json` writes them for further
processing.

# Insert Throughput Benchmark

Benchmark tool for measuring MDDB document insertion throughput. Inserts documents in configurable batches, records timing per batch, and generates an HTML report with an SVG chart.

## Prerequisites

- MDDB server running (default `http://localhost:7890`)
- Go 1.27+

## Build

```bash
cd tools/bench
go build -o mddb-bench .
```

## Usage

```bash
# Start MDDB
cd services/mddbd
go run . -db /tmp/bench.db

# Run benchmark (default: 10K docs, batches of 100)
cd tools/bench
./mddb-bench

# Custom parameters
./mddb-bench -total 5000 -batch 50 -collection mybench -output results.html

# Cleanup collection after benchmark
./mddb-bench -total 1000 -cleanup
```

## Flags

| Flag           | Default                    | Description                        |
|----------------|----------------------------|------------------------------------|
| `-url`         | `http://localhost:7890`    | MDDB server URL                    |
| `-collection`  | `bench`                    | Collection to insert into          |
| `-total`       | `10000`                    | Total documents to insert          |
| `-batch`       | `100`                      | Batch size for timing measurements |
| `-output`      | `bench_report.html`        | HTML report output path            |
| `-cleanup`     | `false`                    | Delete collection after benchmark  |

## What It Measures

Each document is a simulated blog post with:
- Random title (3-6 words)
- Random tags (1-3 from a pool of 20)
- Random author
- 2-5 paragraphs of lorem ipsum (~500-2000 characters)

Documents are inserted one-by-one via `POST /v1/add`. Every batch of N documents is timed and throughput is calculated.

### Observations

- **0-2K docs**: Stable ~37-49 docs/sec. BoltDB is small, FTS index fits comfortably.
- **2K-5K docs**: Throughput drops to 11-25 docs/sec. FTS token index grows, BoltDB page splits and fsync become expensive.
- **5K-10K docs**: Recovery to ~33-38 docs/sec. BoltDB has compacted and stabilized at a larger page count.
- **Batch 40 dip (4000 docs)**: 9.3s for 100 docs (11 docs/sec) — classic BoltDB B+ tree rebalancing spike.
- Each insert includes: JSON decode, BoltDB write, FTS tokenization + index update, revision tracking, checksum computation.
